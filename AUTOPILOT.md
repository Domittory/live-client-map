# Autonomous Development Workflow

## Project context

Прочитай:

- AGENTS.md
- CLAUDE.md
- SPEC.md
- все тикеты в `.scratch/live-client-map/issues/`

Эти файлы являются источником истины для проекта.

Не полагайся на память предыдущих сессий.
После запуска новой сессии заново оцени состояние проекта по файлам.

---

# Ticket workflow

Работай с тикетами начиная с 09.

Твоя задача — автономно выполнять тикеты, соблюдая зависимости и правила безопасности.

---

## Selecting tickets

Если пользователь не указал конкретный номер тикета:

Найди первый тикет с номером >= 09, у которого:

- Status не равен resolved.
- Все тикеты из Blocked by имеют Status resolved.
- Тикет не занят другим агентом.

Перед выбором тикета:

Проверь:

- текущий Status;
- Blocked by зависимости;
- последние изменения файлов;
- нет ли другого агента, работающего над этим тикетом.

---

## Explicit ticket assignment

Если пользователь явно указал номер тикета:

Например:

"Работай над тикетом 17"

Тогда:

- работай только над этим тикетом;
- не переключайся автоматически на другие тикеты;
- не выбирай другой тикет вместо него.

Если тикет заблокирован:

Остановись и объясни:

- какие блокеры существуют;
- почему нельзя продолжить;
- какие тикеты должны быть завершены.

Неправильно:

"Тикет 17 заблокирован, поэтому я начну тикет 12."

Правильно:

"Тикет 17 заблокирован тикетами 12, 13 и 14. Останавливаюсь."

---

# Working with multiple agents

В проекте могут одновременно работать несколько AI-агентов.

Например:

- Claude Code;
- Kimi Code;
- Codex;
- другие агенты.

Считай неожиданные изменения возможными изменениями другого агента.

Если обнаружены изменения, которые сделал не ты:

Не делай:

- revert;
- удаление;
- перезапись;
- массовое форматирование;
- исправление чужого тикета.

Сначала выясни:

- кто владелец изменений;
- какой тикет выполняется;
- относятся ли изменения к текущей задаче.

Не изменяй файлы другого агента без явной необходимости.

---

# Before starting a ticket

Перед началом:

1. Прочитай полный текст тикета.
2. Прочитай все Blocked by тикеты.
3. Изучи существующий код.
4. Проверь соответствие SPEC.md.
5. Сформируй краткий план реализации.

Перед началом работы измени:

```
Status: claimed
```

---

# Implementation

Реализуй только текущий тикет.

Не расширяй область работы без необходимости.

Не меняй архитектуру без основания.

Не добавляй новые технологии без согласования.

---

# Architecture decisions

Никогда не принимай молча архитектурные решения.

Если выбор влияет на:

- database schema;
- authentication;
- security;
- API contracts;
- technology choices;
- data models;

остановись.

Покажи:

1. Возможные варианты.
2. Плюсы и минусы.
3. Рекомендуемый вариант.
4. Риски.

Жди подтверждения пользователя.

После подтверждения:

- зафиксируй решение в тикете;
- продолжай реализацию.

Если решения нет в SPEC.md или ранее решённых тикетах — не придумывай его самостоятельно.

---

# Database rules

Для любых изменений базы данных:

Объясни:

- какие таблицы меняются;
- какие поля добавляются;
- какие RLS политики меняются;
- влияет ли это на существующие данные.

Разрешено автономно:

- создавать migration files;
- читать схему;
- анализировать данные.

Требует подтверждения:

- supabase db reset;
- удаление данных;
- destructive migrations;
- изменение production базы.

Никогда не отключай:

- RLS;
- authentication;
- authorization;

только чтобы исправить ошибку.

---

# Testing

После реализации выполни необходимые проверки:

- lint;
- typecheck;
- unit tests;
- integration tests;
- smoke tests.

Не считай тикет завершенным только после написания кода.

Тикет завершён только когда:

- acceptance criteria выполнены;
- проверки пройдены;
- результат записан.

---

# Completing a ticket

После успешного завершения:

Измени:

```
Status: resolved
```

Добавь раздел:

```
## Implementation result
```

В нём укажи:

- что сделано;
- какие файлы изменены;
- какие проверки пройдены;
- известные ограничения.

# Git workflow

Git является источником истории изменений.

Перед крупными изменениями:

Проверь:

```
git status
```

Перед началом крупного тикета создай checkpoint:

```
git add .
git commit -m "checkpoint before ticket XX"
```

После завершения тикета:

```
git add .
git commit -m "ticket XX completed"
```

Не выполняй без подтверждения:

- git reset --hard;
- git clean;
- git push;
- удаление истории Git.

---

# Autonomous mode

Работай автономно для обычных инженерных задач.

Не спрашивай подтверждение для:

- чтения файлов;
- поиска по проекту;
- git status;
- git diff;
- lint;
- typecheck;
- тестов;
- установки зависимостей проекта;
- форматирования файлов текущего тикета.

Спрашивай подтверждение только для:

- архитектурных решений;
- системных изменений;
- установки системных инструментов;
- Docker;
- Homebrew;
- Colima;
- изменения окружения;
- database reset;
- удаления данных;
- опасных Git операций.

---

# Safety rules

Никогда не выполняй без явного подтверждения:

- rm -rf;
- git reset --hard;
- git clean;
- git push;
- удаление файлов проекта;
- destructive database migrations;
- очистку production данных.

---

# Scope control

Не изменяй файлы вне текущего тикета без необходимости.

Не запускай:

```
prettier --write .
```

для всего проекта.

Предпочитай:

форматировать только файлы текущего тикета.

Не изменяй без необходимости:

- SPEC.md;
- AGENTS.md;
- CLAUDE.md;
- AUTOPILOT.md;
- файлы других тикетов.

---

# Session continuation

После `/clear` или новой сессии:

Не используй память предыдущего чата.

Заново прочитай:

- SPEC.md;
- AGENTS.md;
- CLAUDE.md;
- AUTOPILOT.md;
- текущие тикеты;
- Git status.

Продолжай работу только на основании состояния проекта.
