# Dependency security gate

Тикет 03. Этот документ объясняет, как устроена проверка безопасности
production-зависимостей и как оформить временное исключение.

## Что проверяется

`pnpm security:audit` запускает `pnpm audit --prod` по release lockfile и
падает, если в **production**-зависимостях есть уязвимости уровня `critical`
или `high`.

Development-зависимости (lint, тесты, сборка) в этот gate не входят: уязвимость
в инструменте разработки не должна блокировать релиз, а production-уязвимость не
должна прятаться за шумом dev-дерева. Их состояние видно через `pnpm audit` без
флага `--prod`.

Проверка подключена в CI (job `quality`, шаг
`Production dependency security gate`) и блокирует pipeline при новом
`critical`/`high` finding.

## Как исправить

1. Обновить уязвимый пакет до пропатченной версии (`pnpm why <пакет>` покажет,
   кто его тянет).
2. Если это транзитивная зависимость без прямого обновления — добавить точечный
   override в `pnpm.overrides` в `package.json` (например, `"postcss@<=8.5.22":
   "8.5.26"`).
3. Пересобрать lockfile и прогнать проверки.

## Временное исключение

Если исправление требует отдельной работы, риск можно принять явно и на срок.
Исключения лежат в `.security-audit-exceptions.json`:

```json
{
  "exceptions": [
    {
      "id": "GHSA-xxxx-xxxx-xxxx",
      "reason": "Почему риск принят и какая работа его закрывает",
      "owner": "кто отвечает за решение",
      "expiresAt": "2026-01-31T00:00:00.000Z"
    }
  ]
}
```

Правила:

- обязательны все четыре поля: `id`, `reason`, `owner`, `expiresAt`;
- `id` — это GHSA-id, npm advisory id или имя пакета;
- после `expiresAt` исключение **перестаёт действовать**: gate снова падает и
  пишет `exception expired`, то есть риск нужно пере-подтвердить, а не
  унаследовать молча;
- исключение без owner/срока/основания считается ошибкой конфигурации, и gate
  завершается с кодом 2.

## Коды выхода

| Код | Значение                                              |
| --- | ----------------------------------------------------- |
| 0   | блокирующих уязвимостей нет                           |
| 1   | есть `critical`/`high` без действующего исключения     |
| 2   | gate не смог выполниться (нет отчёта, битый JSON и т.д.) |
