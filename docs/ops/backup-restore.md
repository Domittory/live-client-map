# Резервное копирование и восстановление

Решение (тикет 63, согласовано с владельцем): резервирование через **встроенные механизмы
Supabase Cloud** — автоматические ежедневные бэкапы и Point-in-Time Recovery (PITR). Отдельный
`pg_dump`-пайплайн не заводится.

Требования тикета 05: бэкапы шифруются, ротация ~30 дней, удалённые данные исчезают из бэкапов в
пределах 30 дней.

## Что резервируется

- Полная база Postgres: данные, схема, роли и пользователи `auth`.
- Бэкапы Supabase шифруются в хранилище (AES-256) и доступны только владельцу/администраторам
  проекта Supabase — не через приложение и не через роль `anon`/`authenticated`.
- Объектное хранилище (Storage buckets) сейчас не используется приложением (0 buckets), поэтому
  отдельной процедуры для файлов нет.

## Целевые RPO / RTO

| Метрика | Цель                     | Чем обеспечивается                      |
| ------- | ------------------------ | --------------------------------------- |
| RPO     | ≤ 24 ч (≤ 15 мин с PITR) | ежедневный бэкап + PITR (при включении) |
| RTO     | ≤ 1 ч                    | восстановление + post-deploy smoke      |

Точные цифры подтверждаются планом Supabase при подключении проекта; здесь зафиксированы цели,
по которым проводится restore drill.

## Процедура восстановления

1. Определить точку восстановления (время до сбоя/ошибочной миграции).
2. В Supabase Dashboard → Database → Backups: либо восстановить ежедневный бэкап, либо выбрать
   момент PITR.
3. Дождаться завершения восстановления (статус виден в Dashboard).
4. Прогнать smoke и проверки:
   ```bash
   ./scripts/post-deploy-smoke.sh <BASE_URL>
   pnpm test:integration   # против восстановленной базы
   ```
5. Записать факт восстановления и точку восстановления в журнал инцидента.

Тот же результат достигается из CLI (`supabase db restore`), но Dashboard даёт наглядный статус и
меньше шансов на ошибку.

## Restore drill

Проводится регулярно (не реже раза в месяц) и после крупных релизов, чтобы доказать, что
восстановление реально работает, а не только описано:

1. На staging-проекте создать контрольную запись (org/client с уникальной меткой).
2. Сделать бэкап (или дождаться планового ежедневного).
3. Удалить/изменить контрольную запись.
4. Восстановить из бэкапа по процедуре выше.
5. Убедиться, что контрольная запись вернулась в целостном виде (все связанные таблицы).
6. Подписать результат в [release-checklist.md](./release-checklist.md).

## Связь с erasure (тикет 05, 58)

- Hard delete клиента (тикет 58) удаляет данные из основной базы сразу; audit-трейл обезличивается.
- Из бэкапов данные исчезают по мере ротации (≤ 30 дней) — это удовлетворяет требованию «удаление
  из бэкапов в течение 30 дней».
- `erasure_requests.backup_marker` фиксирует момент/маркер бэкапа на время erasure, чтобы при
  аудите можно было доказать, после какого бэкапа данные клиента уже отсутствуют в резервных
  копиях.
